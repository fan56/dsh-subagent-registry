# dsh-subagent-registry

[English](./README.en.md)

Регистрирует пользовательских агентов, определённых в `~/.dsh/agents/*.md`
(метаданные во frontmatter + markdown-тело как persona/system prompt), как
суб-агентов [dsh](https://github.com/deepseek-ai/deepseek-harness), вызываемых по
имени: основной диалог вызывает их через `use_agent`, а `ask_agent` задаёт вопрос
фоновому агенту и ждёт ответа. Работает на встроенном provider `spawn` — чистый
плагин, не меняет сам dsh.

## Возможности

- **Один markdown-файл — один агент** — во frontmatter модель/уровень thinking,
  тело — system prompt, изменения вступают в силу сразу.
- **Продолжение с места прерывания** — после прерывания длинной задачи (ошибка/
  отмена/лимит/сбой) повторный вызов автоматически продолжает с сохранённого
  промежуточного прогресса, а не начинает заново.
- **Делегирование по ролям в приоритете** — использует краткую англоязычную
  инструкцию по делегированию: требует выбрать подходящую пользовательскую роль из
  реестра и передать полный контекст задачи; независимые задачи запускаются в фоне
  параллельно, `subagent_fork` используется только когда нужно обязательно унаследовать
  текущий диалог. Инструкция действует только когда в текущей области видны
  инструменты этого плагина; после удаления плагина восстанавливается официальная
  инструкция.
- **Фоновый запуск + двусторонние уточнения** — `background: true` отправляет
  агента в фон, основной диалог продолжает работать; `ask_agent` шлёт уточняющий
  вопрос и ждёт его ответа.
- **Три агента из коробки** — после установки автоматически внедряются
  `workhorse` / `oldfox` / `rubber-duck` (см. ниже).
- **Поверх официального механизма суб-агентов** — не строит собственный
  исполнитель: каждый пользовательский агент запускается через официальный
  provider `spawn` dsh, то есть суб-агент — это настоящий суб-агент dsh (полная
  сессия, персистентность, continuable). Новые возможности официального стека
  суб-агентов (например, двусторонняя связь) плагин наследует автоматически;
  официальный инструмент `subagent` остаётся доступным — оба сосуществуют и не
  мешают друг другу.
- **Чистый плагин** — поддерживает публичный механизм суб-агентов линии DSH
  RC/стабильных (проверена совместимость с `0.2.0-rc.2` и `0.2.1-rc.2`), в любой
  момент чисто удаляется; линия alpha больше не поддерживается.

Способ запуска выбирается автоматически по публичным API хоста (обнаружение
возможностей, без ветвления по номерам версий): линия 0.2.1 использует
`startActivation` с доставкой `caller`/`parent` для переднего плана/фона; линия
0.2.0 — `start`/`startContinuable`. При сбое выбранного интерфейса сразу выдаётся
ошибка, повторный запуск через другой интерфейс не выполняется. Запрос запуска на
линии 0.2.1 больше не несёт persona и ограничения инструментов для листовых
агентов — этот плагин на границе `subagent/start` устанавливает зарезервированные
секцию persona и ограничения инструментов в собственную область суб-агента (хост
сам синтезирует те же section/restrict того же окна), семантика соответствует
полям запроса линии 0.2.0. Продолжение на переднем плане использует публичный
`agents.resume`, поддерживает текущую persona/модель/набор инструментов и отмену
вызова, но не занимает слот параллельности manager'а и его нельзя прервать через
`interrupt_agent`; продолженный суб-агент не может связаться с родителем через
штатный `send_message`. Фоновые уточнения по-прежнему управляются manager'ом. Если
чтение или восстановление выбранной старой сессии завершилось ошибкой, выдаётся
ошибка; повторный запуск только при явном `fresh: true`.

## Три предустановленных агента

При первом запуске внедряются в `~/.dsh/agents/` (только если в каталоге ещё нет
разбираемых агентов; ваши изменения никогда не перезаписываются). Это обычные
markdown-файлы, можно менять как угодно.

| Agent | Одной строкой | Типичное применение |
| ----- | ------------- | ------------------- |
| **workhorse** (Трудяга) | Рабочая лошадка: пишет код, расследует, тестирует, разворачивает — вся грязная работа; по умолчанию `deepseek-flash`, защищён от опасных операций | «Пусть workhorse оформит релизный список в таблицу» |
| **oldfox** (Старый лис) | Консультант, который не делает: анализ, trouble shooting, придирчивый review — только контроль, руками не трогает; `glm-5.3` | «Пусть oldfox проверит это решение» |
| **rubber-duck** (Жёлтый утёнок) | Мультимодальный визуальный агент: смотрит скриншоты/графики/рукописный текст, рисует plotext/mermaid/matplotlib; работает на модели с поддержкой изображений | «Попроси rubber-duck посмотреть этот скриншот и извлечь текст страницы» |

## Применение

Установите, перезапустите dsh и просто скажите в диалоге — основная модель сама
выберет агента по имени:

> Пусть workhorse оформит сегодняшний релизный список в таблицу

Под капотом это `use_agent(agent: "workhorse", prompt: "…")`. Фоновому агенту
задают уточняющий вопрос через `ask_agent(agent: "worker", message: "…")` — он
дожидается ответа.

## Управление пресетами суб-агентов

Выберите **Суб-агенты** в левой основной навигации Web — откроется полная страница
управления в главной рабочей области. Страница автоматически читает фактический
`agentsDir` и поддерживает создание, копирование, редактирование, ремонт исходника
и удаление; файлы с ошибками сохраняют диагностику, чтение пустого каталога не
досеивает файлы. Внутреннее имя после создания фиксировано; перед изменением
отображаемого имени запрашивается подтверждение влияния на продолжение или
уточнение по имени в истории.

После успешного сохранения, удаления, открытия или обновления страницы реестр
инструментов для последующих запросов модели обновляется немедленно, а работающие
вызовы сохраняют исходную persona. Если файл менять вручную — откройте страницу
управления или обновите её, чтобы синхронизировать реестр; в чистом CLI/TUI роли
по-прежнему читаются при каждом вызове, статический реестр обновляется при
следующем монтировании.

Сохранение обнаруживает внешние изменения и сохраняет неизвестные поля, комментарии
и неотредактированное тело; файлы, которые нельзя безопасно обновить частично,
переводятся в режим редактирования исходника. Отмена собственного подтверждения
отказа/обновления или сбой сохранения сохраняют черновик. Переход на другие страницы
хоста и обратно позволяет продолжить черновик этого клиента; после перезапуска или
удаления плагина восстановление не гарантируется. Каталог может быть общим для
нескольких профилей — удаление требует подтверждения этого влияния.

Эта клиентская сборка требует пересборки и переустановки; если процесс ещё не
перезагрузил плагин, нужен перезапуск для загрузки новой точки входа клиента.
После загрузки точки входа CRUD пресетов в перезапуске не нуждается.

## Определение собственного агента

Положите файл в `~/.dsh/agents/`:

```markdown
---
name: my-agent
description: "Однострочное описание, показанное в реестре use_agent"
model: opencode-go/deepseek-flash
thinking: high
---

You are my-agent. Этот markdown-текст будет использован дословно как system prompt.
```

Поля frontmatter: `name` (обязательно), `description`, `display_name`, `model`
(`provider/model`, по умолчанию наследование), `thinking`
(`off/low/medium/high/max`, по умолчанию наследование), `deep` (`0` = лист, нельзя
открывать суб-агентов, по умолчанию `1`), `background` (`true` = по умолчанию в
фоне), `maxRounds` (положительное целое, лимит раундов на агента, переопределяет
глобальное `dsh-tui.maxRounds`; потребляется жёстким стоп-механизмом TUI хоста).
Неизвестные поля молча игнорируются.

### Параллельность и лимиты раундов (с 0.1.7)

**Число параллельных и глубину вложенности управляет официальный dsh-subagent**,
плагин не ведёт собственный счётчик параллельности и очередь (единая диспетчеризация
в официальном ActivationManager): `maxActiveSubagents` (лимит одновременно активных
суб-агентов, по умолчанию `8`) и `maxDepth` (лимит глубины вложенности делегирования,
по умолчанию `1`). Оба — volatile-поля, настраиваются на лету без перезапуска:
напишите `subagent: { maxActiveSubagents: N, maxDepth: M }` в patch профиля или
вызывайте в рантайме `settings.update('subagent', …)`. `deep` во frontmatter
`use_agent` лишь ужесточает этот официальный бюджет глубины (`deep: 0` — лист,
убираются все инструменты открытия агентов).

`maxRounds` (лимит раундов на агента) **плагин сохраняет по-прежнему**: у
официального seam суб-агентов нет бюджета раундов, этот ключ продолжает
потребляться жёстким стоп-механизмом TUI хоста.

→ **Полный справочник**: [docs/AGENT-FORMAT.md](./docs/AGENT-FORMAT.md) (на
английском) — валидация и поведение при сбоях каждого поля, семантика
`deep`/`thinking`, механизм продолжения, фоновый запуск, параметры конфигурации,
известные границы.

## Встроенный скилл

Плагин регистрирует в пакете скилл с именем `dsh-subagent-registry-config`
(bundled skill). Когда диалог касается пользовательских суб-агентов, написания
agent `.md`, продолжения суб-агентов или конфигурации этого плагина, dsh
автоматически загружает это руководство по использованию и настройке — основная
модель может по нему писать файлы агентов через `ask_user_question` и настраивать
плагин, не открывая README. Скилл выпускается одной версией с плагином и
поставляется в npm-пакете (`skills/dsh-subagent-registry-config/SKILL.md`).

## Установка

**Требуется dsh >= 0.2.0-rc.2** (линия RC/стабильных; линия alpha больше не
поддерживается). Совместимость проверена с `0.2.0-rc.2` и `0.2.1-rc.2`. Хост
должен монтировать персистентность сессий и сервис `sessionQuery`; продолжение и
уточнения используют формат сессий своей версии, миграция между версиями не
предоставляется.

Способ A — подключить локальный checkout к профилю dsh:

```sh
dsh plugin --profile tui add ~/github/dsh-subagent-registry
```

Способ B — npm-зависимость: `npm i @aiwayds/dsh-subagent-registry`, затем в
конфигурации профиля загрузите плагин под стабильным id
`dsh-subagent-registry` или смонтируйте через bundle patch (как — см.
`cordis.patch.yml` в этом репозитории).

## Удаление

```sh
dsh plugin --profile <name> remove @aiwayds/dsh-subagent-registry
```

Хост уберёт плагин из профиля; после перезапуска dsh инструменты `use_agent` /
`ask_agent` исчезнут. **Файлы агентов в `~/.dsh/agents/` сохранятся** — они
принадлежат вам, повторно не внедряются и не перезаписываются. Без этого плагина
dsh-tui-pi корректно деградирует (теряется только возможность запускать
пользовательских агентов).

## Разработка

```sh
npm run check    # tsc --noEmit
npm run build    # tsc -> lib/
npm test         # регрессионные юнит-тесты и проверка реальной npm-установки во временных каталогах (без LLM)
npm run test:host # реальные сервисы/персистентность/manager/spawn текущего SDK; скриптовая модель, без сети
npm run test:hosts # один и тот же скомпилированный плагин загружается в две реально выпущенные SDK и сверяются версии
```

Инициализация изолированных SDK из каталога плагина (если окружение уже есть,
повторная установка не нужна):

```sh
npm install --prefix ../../.tmp/dsh-type-closure-rc2 --ignore-scripts @deepseek-ai/dsh@0.2.0-rc.2 @deepseek-ai/dsh-session-query@0.2.0-rc.2
npm install --prefix ../../.tmp/dsh-type-closure --ignore-scripts @deepseek-ai/dsh@0.2.1-rc.2 @deepseek-ai/dsh-session-query@0.2.1-rc.2 @deepseek-ai/dsh-working-directory@0.2.1-rc.2
```

Можно указать `DSH_TEST_RC2_CLOSURE_DIR` / `DSH_TEST_021_CLOSURE_DIR` на
`node_modules` другого изолированного окружения; в тестах модель только
скриптуется, сервисы и персистентность — реальные реализации соответствующих
версий.

### Контракт зависимостей `@deepseek-ai/*` (почему optional peer)

Этот репозиторий объявляет **optional peerDependencies** для `@deepseek-ai/*`
(`cordis`, `dsh-subagent`, `dsh-llm`, `schemastery` и т. д.) в выпускаемом пакете
(`>=0.2.0-rc.2 || >=0.2.1-rc.1`). Это намеренное разделение на два уровня:

- **Семантика публикации (для потребителей)**: объявление означает «используй
  одноимённые пакеты, поставляемые хостом, нижняя граница версии
  `>=0.2.0-rc.2 || >=0.2.1-rc.1`». optional peer не устанавливается автоматически
  pnpm/npm, поэтому в `node_modules` профиля не появляется вторая копия, способная
  затенять (shadow) встроенный в хост closure. Опасна именно жёсткая dependency,
  прибитая к старой rc-версии — она ломает загрузку хоста 0.2.x (известный
  сценарий инцидента в сообществе).
- **Typecheck при разработке (для этого репозитория)**: devDependencies
  прибивают новую SDK, `scripts/link-dsh-closure.mjs` (postinstall) симлинкует
  `node_modules/@deepseek-ai/*` на closure, указанный в `DSH_CLOSURE_DIR` или на
  установку глобального dsh, гарантируя одну копию `@deepseek-ai/cordis` в графе
  типов — вторая копия ломает усиление типов `declare module` cordis
  (`Property 'settings' does not exist on type 'Context'`).

Правило поддержки: эти пакеты всегда остаются в форме optional peer — не
возвращать их в dependencies / devDependencies и не убирать `optional: true`
(не-optional peer при включённом `auto-install-peers` в pnpm устанавливается
автоматически, и проблема второй копии возвращается); также не добавлять никаких
жёстких dependencies — прибитая вторая копия тем же образом затеняет closure хоста.

## Интеграционные тесты

`e2e/podman-install/` устанавливает **опубликованные** tarball'ы этого плагина,
dsh-dcp, dsh-cron, dsh-llm-proxy и dsh-profile-switch в контейнере с реальным CLI
dsh, используя реальный npm-клиент со включёнными lifecycle-скриптами зависимостей —
ровно то пересечение, из-за которого упакованный `postinstall` (#2) уехал в релиз
незамеченным. Проверяется, что установка завершается чисто, линковщик closure
отключается в дереве потребителя, реальный хост компонует и поднимает каждый
профиль, и что schema default + явная пустая семантика dcp переживают реальный
слой конфигурации.

- Локально (macOS, podman machine запущен): `e2e/podman-install/run.sh`
- Те же проверки на Linux без podman выполняются еженедельным запланированным
  workflow `e2e install`; `bash e2e/podman-install/entry.sh` работает на любой
  машине с node 22+ и глобальным CLI dsh.
